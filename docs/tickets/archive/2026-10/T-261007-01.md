# T-261007-01 — Decouple remote freshness checks from interactive UI rendering

## Goal
Improve Git Next response time by removing `git ls-remote` and other remote freshness checks from normal UI render paths while preserving fresh remote verification for safety-critical Git actions.

## Do
- Separate cached/local upstream inspection from network-backed remote freshness inspection.
- Normal UI rendering, Help, graph/sidebar refresh, and other read-only interactions must not wait for `git ls-remote`.
- Cache the last known remote freshness result with its update timestamp.
- Reuse an in-flight remote refresh instead of starting duplicate `ls-remote` requests for the same repository/upstream.
- Refresh remote freshness in the background only at controlled points such as repository activation/open, an expired freshness window, or after explicit network operations; do not run `ls-remote` for every local Git state change.
- Keep explicit network operations such as Fetch/Remote refresh responsible for updating the cache.
- Before safety-critical Pull/Push decisions that require current remote truth, allow a forced fresh remote check instead of relying only on stale cache.
- Avoid introducing continuous aggressive polling; network refresh should be event-driven or freshness-based.

## Keep
- Preserve existing Push/Pull Safe Guard behavior and remote-history-rewrite protection.
- Do not weaken safety checks merely to improve perceived speed.
- Preserve offline/VPN/internal-network usability: normal UI must remain usable when the remote cannot be reached.
- Keep existing visible repository state semantics unless the remote freshness value is explicitly stale/unknown.
- Do not change existing user-facing action availability, warnings, confirmations, or Safe Guard outcomes as part of the caching refactor.

## Done
- Opening Help and ordinary sidebar/graph refresh paths do not execute or await `git ls-remote`.
- Repeated UI renders reuse local/cached remote state and respond without remote-network latency.
- Concurrent remote freshness requests for the same target are deduplicated.
- Explicit remote refresh updates the cached freshness state.
- Push/Pull paths can require a fresh remote check when safety depends on it.
- Focused tests cover cached, stale, in-flight deduplication, offline failure, and forced-refresh behavior.
- Full tests, typecheck, and build pass.

## Result
- `inspectCurrentUpstream()` now uses local Git state plus cached remote freshness and no longer executes `git ls-remote` on ordinary UI/read-only paths.
- Added `refreshCurrentUpstreamState()` for explicit/background network freshness checks with a 30-second freshness window and per-repository in-flight deduplication.
- Repository open/activation warms remote freshness in the background without blocking webview rendering.
- Successful Fetch/Remote refresh paths update freshness from the newly fetched tracking ref without an additional `ls-remote` round trip.
- Existing Push/Pull preflight `fetch --prune` safety behavior remains intact and now refreshes the cached upstream state after a successful fetch.
- Added cache clearing and focused repository tests for uncached `unknown`, forced freshness, concurrent refresh reuse, stale detection, fetch-to-healthy transition, and unreachable-remote fallback.
