# Explain force-with-lease before overwrite-style push

## Goal

Make overwrite-style Push safer by explaining force-with-lease in graph and commit terms.

## Do

- When a force-style Push is offered, prefer and explain force-with-lease.
- Show which remote tip must still match for the Push to proceed.
- Explain that a changed remote tip cancels the Push instead of silently overwriting.

## Keep

- Do not enable bare `--force` by default.
- Keep the confirmation read-oriented until the user explicitly confirms.
- Reuse Safe Guard remote-rewrite detection where available.

## Done

- Users see what force-with-lease protects before confirming.
- A mismatched remote tip fails closed with a clear next action.
- Focused tests and build pass.

## Role

worker

## Read

- src/git-safety.mjs

## Depends

## Placement

Offer after a regular Push rejection or a preflight check that shows the remote branch is ahead or diverged.

## Result

Force-with-lease is offered only after a regular Push is rejected or preflight finds incoming/diverged history. The confirmation names the exact remote tip; a changed tip cancels the push. Safe Guard rewrite detection remains a hard block.
