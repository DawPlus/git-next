# Resolve conflicted files and finish Git operations safely

## Goal
Guide users through detecting unmerged files, resolving with VS Code Merge Editor or reviewed bulk acceptance, staging, and completing Merge/Rebase without stale Safe Guard warnings.

## Do
- Detect unmerged/conflicted files from Git status (including UU, AA, DD, AU, UA, DU, UD) and list them clearly in Git Next Source Control or Conflict Helper.
- Add an obvious "Merge Editor로 열기" action for supported conflicted files, using VS Code's built-in Merge Editor and a graceful fallback to normal editor / explanation if unavailable.
- Offer selected-file or all-eligible-files actions: **내 변경 모두 수락** / **수신 변경 모두 수락**, with affected-file preview and explicit confirmation. Handle reversed ours/theirs semantics during Rebase/Cherry-pick and explain unsupported conflicts.
- Show staged progress: **충돌 해결 필요 N건** → **내용 해결 / Stage 필요** → **모든 충돌 해결 완료 / Git 작업 완료 필요** → **Merge 완료**. Determine state from unmerged index entries and in-progress operation markers, not just conflict text.
- When all conflicts are resolved and staged, show the correct **Merge 완료하기** / **Rebase 계속하기** / operation-specific Continue button. Stage alone must not be mistaken for finished Merge; a Merge commit may still be required.
- Update Safe Guard, Conflict Helper and sidebar together after save, Stage, Continue or Abort. When Git confirms completion, show **충돌 해결 완료** and hide stale Continue/Abort recommendations.
- Add a beginner-friendly **Safe Guard conflict guide** with plain Korean copy that tells users what happened, how many conflicts remain, which files need Stage, and the single safest next action. Examples: **충돌 파일 2개를 해결해 주세요**, **모든 파일을 정리했어요. 병합을 마무리할까요?**, **병합이 완료됐어요**.
- Replace bare **Continue / Abort** in the main UI with task-specific action labels: **병합 마무리**, **Rebase 이어서 진행**, **병합 취소하고 이전 상태로 돌아가기**. Keep technical Git command terminology in optional explanations/tooltips.
- Explain side choice in everyday language, e.g. **현재 파일 내용 사용 / 가져온 변경 내용 사용 / 직접 비교하고 선택**, with file-level previews and explicit warnings about discarded edits. Only call a side **로컬/원격** when the actual origin is known; a Merge can be between two local branches and Rebase changes ours/theirs semantics.
- Show **병합 마무리** (Continue) and **병합 취소** (Abort) as direct, visible Safe Guard buttons while a Merge is in progress; use corresponding operation-specific labels for Rebase/Cherry-pick/Revert. Keep cancel available during unresolved conflicts; enable finishing only when Git confirms no unmerged entries remain and prerequisites are met. Never show these buttons outside an active operation.
- Clicking **병합 마무리** must open a confirmation dialog: **모든 충돌을 해결하고 변경 파일을 Stage했나요? 병합을 마무리할까요?** Describe that the remaining Merge commit/Continue step will run; confirmation action **병합 마무리**, secondary action **돌아가기**. If prerequisites fail, show the specific missing steps instead of proceeding.
- Clicking **병합 취소** must open a distinct warning dialog: **진행 중인 병합을 취소하고 병합 시작 전 상태로 돌아갈까요?** Explain that uncommitted conflict-resolution edits may be lost and show the impact/limitations of the actual Git Abort; confirm action **병합 취소하기**, secondary action **계속 해결하기**. Require explicit approval, never treat Abort as ordinary back navigation.
- Disable duplicate submissions, show operation progress and success/failure feedback, and refresh Safe Guard status after either action. Include both dialog flows, button visibility/disable rules, refusal cases, and correct user-facing labels in tests.
- Keep Merge/Rebase/Cherry-pick/Revert Continue and Abort available via existing Conflict Helper, with explicit confirmation for risky actions.
- Add regression tests for conflict detection, editor fallback, bulk accept previews, resolved-but-unstaged, all-staged-but-Merge-still-active, successful Continue, Rebase semantics, and Safe Guard state transitions.

## Keep
- Do not build a custom 3-way diff/merge editor.
- Never automatically accept a side, overwrite user edits, Stage files, or continue/abort Git operations without explicit user confirmation; bulk accept is an opt-in action.
- Keep Abort distinct from completion, and preserve safe behavior on ambiguous/conflicting Git states.
- Do not confuse branch-to-branch Merge with resolving conflict markers.
- Respect existing Git state, safeguards, localization and VS Code compatibility.

## Done
- Users can open Merge Editor, optionally review and accept one side for eligible conflicts, resolve/save/Stage, then complete the Git operation without guessing the next step.
- After all conflict files are staged but a Merge is still in progress, Safe Guard says **충돌 해결 완료 · Merge 완료하기** rather than asking users to resolve conflicts again.
- After Git confirms the operation has completed, show **충돌 해결 완료** and stop suggesting Continue/Abort.
- Non-expert users see both completion and cancellation buttons during an active Merge; each opens its own clear confirmation with consequences and safe defaults. Korean and English copy, button availability, duplicate click safety, and operation-specific choices are covered by regression tests.
- Ordinary file changes do not show conflict actions.
- Tests, typecheck, build, and manual VS Code QA pass.
