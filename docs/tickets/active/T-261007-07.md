# T-261007-07 — Introduce repository snapshot store for instant UI reads

## Goal
Make Git Next interactive UI read repository state from an in-memory snapshot store instead of launching Git subprocesses on panel/menu open, while preserving fresh safety checks at mutation and network boundaries.

## Do
- Introduce a per-repository `RepositoryStore` / snapshot cache keyed by repository root.
- Make read-only UI surfaces consume cached snapshots only:
  - sidebar
  - graph
  - Branch workspace
  - Help/Knowledge live context
  - menus and advisory Safe Guard presentation
- Treat panel/menu open and ordinary render as read-only operations that must not trigger repository Git subprocesses when a snapshot already exists.
- Load an initial repository snapshot when a repository is first observed/opened.
- Refresh only affected snapshot fields after known state-changing events:
  - Commit
  - checkout / switch / branch create / branch delete
  - stash / apply / pop
  - merge / rebase / cherry-pick / revert / continue / abort
  - Fetch / Pull / Push
  - external working-tree or Git state changes from the VS Code Git API
  - explicit user Refresh
- Keep refresh granular where practical. Local working-tree changes must not force commit-history, linked-worktree, or remote-freshness reads.
- Make successful mutations refresh the relevant snapshot before subsequent Safe Guard guidance or UI rendering.
- Preserve T-261007-01 remote freshness behavior:
  - ordinary UI reads cached remote state
  - Fetch / Pull / Push / explicit remote refresh update remote-related snapshot fields
  - safety-critical network operations may force the minimum required fresh remote check immediately before execution
- Move or reuse T-261007-05 in-flight deduplication inside store refreshes so concurrent consumers share refresh work.
- Prevent an older in-flight refresh from overwriting a snapshot produced after a mutation or later refresh generation.
- Keep repository snapshots isolated across multi-root / multi-repository workspaces.
- Define a compact invalidation/refresh map documenting which fields each mutation/event refreshes.
- Target zero Git subprocesses for opening an already-initialized read-only UI surface.

## Keep
- Preserve current visible behavior, Safe Guard outcomes, confirmations, warnings, action availability, and beginner guidance.
- Do not weaken force-push, remote-history-rewrite, dirty-working-tree, detached-HEAD, protected-branch, or in-progress-operation safeguards.
- Do not trust stale cached remote state for safety-critical network mutations when a fresh check is required.
- Do not introduce a long-lived disk cache. Repository snapshots are process-memory state and are rebuilt when needed.
- Preserve offline usability.
- Preserve existing multi-root repository selection behavior.
- Existing T-261007-01 through T-261007-06 work should be reused or absorbed rather than duplicated.

## Done
- Opening sidebar, graph, Branch, Help, and ordinary Git Next menus against an initialized repository performs no repository Git subprocess solely for rendering.
- Commit and other successful mutations refresh the required cached fields before subsequent Safe Guard/UI reads.
- Fetch/Pull/Push refresh remote-related cached state at the correct boundaries.
- External Git/working-tree changes update the relevant cached fields through the existing VS Code Git event path.
- Concurrent refresh requests for the same repository share work.
- Stale in-flight refreshes cannot overwrite newer post-mutation snapshots.
- Different repository roots never share snapshots.
- Focused tests cover initial load, cache-only UI reads, mutation refresh, network refresh, external-change refresh, stale-generation protection, and multi-repository isolation.
- Full tests, typecheck, and build pass.

## Refresh map
- Repository observed/opened -> full snapshot bootstrap.
- Ordinary sidebar / graph / Branch / Help / menu open -> cache read only; refresh only on cache miss.
- Commit / undo / discard / stage mutations routed through the mutation boundary -> invalidate in-flight state, run Git, refresh snapshot, then render.
- Branch create / switch / rename / delete / merge / tracking changes -> refresh snapshot before Branch UI rerender.
- Fetch / Pull / Push / first Push / force-with-lease -> update remote state, refresh snapshot, then render result.
- VS Code Git repository state change -> debounce, refresh affected repository snapshot, then rerender live webviews.
- Explicit Refresh -> refresh remote state, refresh repository snapshot, then render.
- Safety-critical preflight checks may still execute direct fresh Git reads immediately before mutation.

## Result
- Added an in-memory repository snapshot store in `extension-core.ts`, keyed by repository root.
- `getState()` now returns the cached snapshot when available and performs a refresh only on cache miss.
- Added `refreshState()` with in-flight deduplication, snapshot version/updatedAt metadata, and per-repository generation protection.
- Removed the global generation coupling so mutations in one repository do not invalidate another repository's refresh.
- Added a short 250ms completed-refresh reuse window for external Git event bursts to avoid duplicate Branch/global refreshes.
- Repository open/observe now bootstraps a snapshot in the background.
- Internal mutation boundaries refresh the snapshot after Git completes.
- Sidebar Commit now runs through the mutation boundary, so subsequent Safe Guard/UI reads use refreshed repository state.
- Push/Pull, first Push, force-with-lease, Push-before-Pull, and diverged Merge refresh the snapshot before rendering their result.
- Branch and Help panels now read through the shared snapshot store instead of performing their own repository-state Git reads.
- Branch panel creation now happens before action/workflow module loading so the panel becomes visible immediately.
- Removed the obsolete Help-specific repository loader.
- Added focused regression coverage in `test/repository-snapshot-store.test.mjs` and updated T-04/T-05 compatibility tests.
